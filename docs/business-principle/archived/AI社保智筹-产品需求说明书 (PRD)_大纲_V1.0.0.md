## 4. 功能需求

### 4.1 动态政策库与多源采集系统 ⬅️ 核心模块

| 需求项 | 说明（待细化） | 优先级 |
|--------|---------------|--------|
| 4.1.1 政策数据源分级标准 | 将信源划分为 HIGH（政府官网）/ MEDIUM（官媒、12333）/ LOW（短视频、公众号、微博），定义每级的准入条件和变化检测频率 | P0 |
| 4.1.2 多源自动化采集 | 对 HIGH 源定期爬取 + 变更检测；对 LOW 源提供 AI 提取 + 置信度标记管道 | P0 |
| 4.1.3 政策文本结构化抽取 | 从非结构化文本中提取 {政策类型, 适用人群, 地区, 金额/比例, 条件, 有效期} | P0 |
| 4.1.4 行政区划标准化 | 统一使用 GB/T 2260 6 位行政区划代码，支持省/市/区/街道级联查询 | P0 |
| 4.1.5 政策版本快照 | 每次变更生成 immutable 快照，支持按时间回溯历史方案 | P0 |
| 4.1.6 短视频/语音信源处理 | 音频提取 → ASR → OCR 字幕 → 文本管道 | P1 |

### 4.2 AI 政策交叉验证引擎 ⬅️ 核心模块

| 需求项 | 说明（待细化） | 优先级 |
|--------|---------------|--------|
| 4.2.1 语义检索比对 | 新政策 claim 与已存库 embedding 检索 top-5 相似政策，逐字段 Diff | P0 |
| 4.2.2 置信度评分模型 | 多源加权投票公式（匹配数 × 权重 - 冲突数 × 惩罚） | P0 |
| 4.2.3 三级入库决策 | ≥0.85 自动 verified / 0.6–0.85 待人工审核 / <0.6 标记 unverified 保留 | P0 |
| 4.2.4 人工审核工作台 | 待审队列、冲突高亮、一键确认/驳回 | P1 |
| 4.2.5 用户反馈闭环 | 用户可上报政策偏差，反向调低信源权重 | P1 |

## 5. 非功能需求

### 5.1 数据安全与隐私合规 ⬅️ BRD 未覆盖，PRD 必须补充

| 需求项 | 说明（待细化） |
|--------|---------------|
| 5.1.1 个人信息保护 | 遵循《个人信息保护法》(PIPL)，明确信息收集最小必要原则、用户授权协议、撤回同意机制 |
| 5.1.2 数据分级与加密 | 身份证号、银行卡号等敏感信息强制国密 SM4 加密存储；传输层 TLS 1.3 |
| 5.1.3 数据本地化 | 所有社保相关个人数据存储在中国境内 |
| 5.1.4 用户授权管理 | 微信授权（手机号/位置）、实名认证的授权状态管理和撤回能力 |
| 5.1.5 日志审计 | 所有用户数据访问操作留痕，支持安全审计 |
| 5.1.6 密钥管理 | 敏感配置通过密钥管理服务注入，禁止明文入代码 |

### 5.2 性能与可用性

| 需求项 | 目标值（待确认） |
|--------|----------------|
| 政策匹配响应时间 | < 3 秒 |
| 方案生成响应时间 | < 10 秒 |
| 小程序首屏加载 | < 2 秒 |
| 系统可用性 | 99.5%（非生产）/ 99.9%（生产） |
| 政策库更新时效 | HIGH 源变更后 < 24 小时入库 |

### 5.3 可扩展性

| 需求项 | 说明（待细化） |
|--------|---------------|
| 新城市接入 | 配置化接入，新增城市不修改核心匹配逻辑 |
| 信源扩展 | 新数据源类型可通过插件式管道注册 |
| 匹配引擎 | 规则引擎与 ML 模型解耦，支持独立迭代 |
